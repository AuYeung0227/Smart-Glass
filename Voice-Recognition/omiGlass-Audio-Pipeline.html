01

麦克风与 PDM

链路的起点：模拟声音如何变成数字

Q01PDM 是什么？

Pulse Density Modulation（脉冲密度调制），数字 MEMS 麦克风的默认输出格式。输出永远是 1 bit——幅度信息不在单个比特的值里，而在一串比特的疏密里。

波形位置PDM 位流（16 bit 窗口）1 的比例代表幅度
波峰1111111111111111100%正向满量程
上升111111111111000075%+50%
零点111111110000000050%0（静音）
波谷00000000000000000%负向满量程

对比 PCM：PCM 用「一个样本 = 一个大数字」编码，PDM 用「时间上的比例」编码。

Q02为什么数字麦克风都用 PDM？

本质是一次复杂度的转移：

  • 做一个 16-bit SAR ADC 需要精密电容匹配、稳定基准、讲究的模拟布线——在 MEMS 那片小硅上又难又贵
  • 做一个 1-bit Sigma-Delta 本质上只需要一个比较器——精度从时间上来（高速时钟分频/计数是数字电路，又准又便宜）
用「数字的复杂度」换掉「模拟的复杂度」——这是 PDM 统治 MEMS 麦克风的根本原因。

附带好处：只要 2 根线（CLK + DATA）、天生抗混叠、麦克风是纯数字外设。

Q03bits_per_sample 是什么？

mic.cpp:48 —— .bits_per_sample = I2S_BITS_PER_SAMPLE_16BIT

要分清两个「位宽」：

  1. 麦克风输入的 PDM 是 1 bit —— 原始的一串 0/1 脉冲
  2. bits_per_sample 说的是抽取之后的输出位宽 —— ESP32 内部滤波抽取后，每个 PCM 样本用 16 位表示（−32768…32767）

PDM 是「1 bit 进、16 bit 出」。它决定了后面整条链路都用 int16_t：

位置依赖
缓冲int16_t *i2s_read_buffer，每样本 2 字节
增益限幅32767 / -32768（mic.cpp:132-135）
Opus 配置OPUS_SET_LSB_DEPTH(16)

三者必须一致，改一个就要全改。

Q04PDM 输入 1 bit，怎么变成 16 bit？是把时间叠加吗？

本质是「在时间窗口内数密度」，不是「叠加」。前提是 PDM 时钟比目标采样率快很多（过采样），所以一个 16-bit 输出样本对应 N 个 1-bit 输入。

把 1 记 +1、0 记 −1，对窗口内求和：

64 个 bit 的情况1 的个数求和还原幅度
全是 164+64+满量程
一半 1 一半 03200（静音）
全是 00−64−满量程

严谨说法是抽取滤波器（decimation filter）：低通滤波 + 降采样两合一，硬件里常用 CIC（级联积分梳状）滤波器实现——但直觉完全一样：窗口内数密度 = 该时刻的幅度。

Q05输出采样率和 PDM 输入的一样吗？

不一样，采样率变了，而且是大幅降低。

  • PDM 输入：1-bit 数据流，速率单位是 bit/s
  • 抽取输出：16-bit PCM，速率单位是 样本/s = 16 kHz

两者由过采样率（OSR）关联。以通用 PDM 麦克风的 64× 为例：PDM 比特流 1.024 Mbit/s，PCM 输出 16 kHz——每 64 个 1-bit 进、出 1 个 16-bit 样本。

纠错：ESP32-S3 的硬件下采样器有自己的档位（ESP-IDF 的 i2s_pdm_dsr_t：DSR_8S / DSR_16S），PDM 时钟是采样率的十几到几十倍，不是固定的 64×。64× 是通用 PDM 麦克风的典型值。核心结论不变：PDM 是「高速 1-bit 进、低速 16-bit 出」，用高速率换位数。

Q06为什么定义了 16k，PDM 流还要乘以 64？

因为 16000 是「你要求的输出规格」，×64 是「硬件为了用 1-bit 麦克风满足这个规格付出的代价」。

  1. 1 bit 表示不了幅度——只有 0/1 两个状态，等价于 ~6 dB 信噪比，完全不能用
  2. 解法：把「一个点的精度」换成「一段时间里的密度」——每输出 1 个 16-bit 样本，让麦克风送 64 个 1-bit 值
  3. 交易本质：比特率反而下降了（1.024 Mbit/s → 256 kbit/s），但每个样本的位数上升了（1 bit → 16 bit）——用「快而粗」换「慢而精」

那为什么不能只靠过采样凑到 16 bit？理论上要 2¹⁶ ≈ 65536 倍过采样（1 GHz 时钟），不现实。真正让它可行的是 Sigma-Delta 噪声整形：

做法（64× 过采样）有效精度
只有过采样~4 bit ✗
一阶噪声整形~9 bit
二阶噪声整形（主流 MEMS）~14 bit ✓

「过采样 + 噪声整形」一起，才把 1 bit 变成可用的十几个 bit。

02

I2S 外设与 DMA

芯片内部：从 1-bit 流到内存里的 PCM

Q07三个 I2S 配置项各是什么？

i2s_config_t i2s_config = {
    .mode = (i2s_mode_t) (I2S_MODE_MASTER | I2S_MODE_RX | I2S_MODE_PDM),
    .sample_rate = MIC_SAMPLE_RATE,
    .bits_per_sample = I2S_BITS_PER_SAMPLE_16BIT,
    .channel_format = I2S_CHANNEL_FMT_ONLY_LEFT,
    .communication_format = I2S_COMM_FORMAT_STAND_I2S,   // ①
    .intr_alloc_flags = ESP_INTR_FLAG_LEVEL1,
    .dma_buf_count = 8,                                  // ②
    .dma_buf_len = 256,                                  // ③
    .use_apll = false,
    .tx_desc_auto_clear = false,
    .fixed_mclk = 0,
};

① communication_format —— 选串行线路的时序格式（这里是飞利浦标准 I2S）。但在 PDM 模式下基本是「摆设」：PDM 不用 I2S 那套「WS 分左右声道 + BCK 逐位对齐」的框架，它只有一条数据线，WS 引脚被复用成 PDM 时钟。

② dma_buf_count = 8 —— 环分成几块（决定通知/读取粒度）
③ dma_buf_len = 256 —— 每块装多少样本

合起来就是一个硬件自动填充的环形缓冲：

8 × 256 = 2048 样本 ÷ 16000 Hz ≈ 128 ms

Q08DMA 的作用是什么？

DMA = Direct Memory Access，一块硬件搬运工，能在不占用 CPU 的情况下把数据从外设搬进内存。

麦克风是连续不断在产数据的（不管 CPU 忙不忙）。没有 DMA，CPU 就得亲自盯着一个个收，腾不出手做别的。DMA 让外设自己把数据流写进 RAM 环形缓冲，CPU 只在方便的时候去取——CPU 和采样时钟被彻底解耦。

那 128 ms 容量的作用：CPU 因照片 BLE 上传等卡住时，DMA 照填，水位抬升；CPU 回来一次性排空。只要卡顿 < 128 ms，一帧不丢；超过就绕回覆盖最旧数据 → 丢样、杂音。

本项目 i2s_driver_install(I2S_PORT, &i2s_config, 0, NULL) 传 0, NULL，意味着没有事件队列/回调，是纯轮询模式。DMA 在后台默默搬运，只是「什么时候取走」由软件决定。

Q09这个 DMA 是「双缓冲队列」吗？

不是双缓冲。dma_buf_count = 8 —— 是 8 缓冲环形队列。双缓冲（N=2 乒乓）是特例：DMA 写 A 时 CPU 读 B，填满就交换。N=8 是同一个思路的推广：总容量 = 余量。

N 小（=2）N 大（=8）
RAM 占用少多
延迟低略高
抗 CPU 抖动差 ✗好（128ms 余量） ✓

本项目主循环是软实时超级循环（还要跑照片上传、OTA、LED、按键），N=2 那点余量扛不住。

哪里体现？项目里其实有三层缓冲，每层都在做同一件事：

层位置容量解耦谁和谁
① DMA 环mic.cpp:52128 ms麦克风硬件 ↔ CPU
② PCM 环opus_encoder.cpp:13,31500 ms麦克风回调 ↔ Opus 编码器
③ 发送环app.cpp:8316 帧Opus 编码器 ↔ BLE 发送

代码模式完全一样：写指针 + 读指针 + 取模回绕。

Q10DMA 相关的代码在哪？

先说清楚：DMA 环形缓冲本身不在项目代码里——它是 ESP-IDF 驱动在 i2s_driver_install() 时 malloc 出来的。项目只做了四件事：

步骤位置代码
配置mic.cpp:52-53.dma_buf_count = 8, .dma_buf_len = 256
安装（真正分配）mic.cpp:68i2s_driver_install(I2S_PORT, &i2s_config, 0, NULL)
清空mic.cpp:82i2s_zero_dma_buffer(I2S_PORT)
读出mic.cpp:122i2s_read(..., &bytes_read, pdMS_TO_TICKS(20))

读出代码全貌（mic.cpp:114-144）：

void mic_process()
{
    if (!mic_running || i2s_read_buffer == nullptr) return;

    size_t bytes_read = 0;
    esp_err_t err =
        i2s_read(I2S_PORT, i2s_read_buffer, MIC_BUFFER_SAMPLES * sizeof(int16_t), &bytes_read, pdMS_TO_TICKS(20));

    if (err == ESP_OK && bytes_read > 0) {
        size_t samples_read = bytes_read / sizeof(int16_t);   // 用【实际】数量

        if (MIC_GAIN != 1) {
            for (size_t i = 0; i < samples_read; i++) {
                int32_t sample = (int32_t) i2s_read_buffer[i] * MIC_GAIN;
                if (sample > 32767)  sample = 32767;
                if (sample < -32768) sample = -32768;
                i2s_read_buffer[i] = (int16_t) sample;
            }
        }

        if (audio_callback != nullptr) {
            audio_callback(i2s_read_buffer, samples_read);
        }
    }
}

Q11DMA 搬的是原始 PDM 还是 PCM？PCM 给谁用？

前提反了——DMA 搬的恰恰就是处理好的 16-bit PCM。转换发生在 DMA 之前，由硬件完成。
麦克风 I2S 外设（芯片内部） CPU / 软件 ┌────────┐ │ MEMS │ PDM 1-bit ┌───────────────┐ │ 传感器 │ ─────────────▶ │ sinc 滤波器组 │ 16-bit PCM ┌──────┐ │ +Σ-Δ │ CLK ◀──────── │ + 下采样 │ ────────────▶ │ DMA │ ─▶ RAM └────────┘ └───────────────┘ (16 kHz) └──────┘ ↑ 转换在这里（硬件） ↑ 只搬 PCM

证据：ESP32-S3 TRM 里有寄存器 I2S_RX_PDM_SINC_DSR_16_EN，文档原文「配置 PDM RX 滤波器组 模块的下采样率」——「滤波器组」直接证明芯片里有专门的硬件滤波模块在做转换。

为什么 DMA 不可能搬原始 PDM：

  1. DMA 的搬运单位是「字」不是「位」 —— 它按 8/16/32 位搬运，而 PDM 是串行比特流，必须先被外设组装成并行字
  2. PDM 根本不在内存总线上 —— 它只存在于引脚和 I2S 移位寄存器里
  3. 让 CPU 做抽取滤波是巨大浪费 —— 这正是硬件滤波器存在的意义
副产品证据：dma_buf_len 的单位是样本。如果 DMA 搬的是 PDM 位，256 就该解释成 256 个 bit = 16 个 PCM 样本，整个 128 ms 的算法就错了。8×256=128ms 正好和软件「一次读 100ms」严丝合缝——说明 DMA 在按 PCM 样本计数。

PCM 给谁用？—— 给软件用。

i2s_read() → mic_process() → 增益 → onMicData() → opus_receive_pcm() → Opus 编码 → BLE → 手机 App（解码回 PCM → 播放 / 语音识别 / 情感分析）

更深一层：为什么必须有 PCM 这个中间格式？因为 PCM 是软件世界的通用货币，PDM 不是——没有任何软件能直接吃 PDM（没法做 FFT、喂 MFCC、训练模型）。转换放在硬件边界的意义：让 DMA 之后的一切都只说 PCM 一种语言。

Q12i2s_read 是一次性把 DMA 里 8×256 全读出来吗？

不是。一次最多读 1600 个样本（请求上限），实际通常只读到几百个。读多少由三个因素决定：

因素值作用
① 请求量1600 样本硬上限
② DMA 里有货动态得攒够才可能读满
③ 超时20 ms等不到就先返回部分

2048（DMA 总容量）根本不在这三个因素里——它是库存，不是单次提货量。

DMA 总容量 2048 样本 (128ms) ← 最多能攒多少 请求上限 1600 样本 (100ms) ← 一次最多读多少 20ms 实际产出 320 样本 ← 通常实际读到多少

纠正心理模型：DMA 不是「攒满 2048 → 一次性全倒出 → 再攒满」，而是永远在写、绕圈；软件持续小口小口地舀；i2s_read 只推进读指针，写指针完全不受影响。

代码证据：mic.cpp:125 用的是 bytes_read（实际值）而不是硬编码 1600——如果真的一次读满 2048，这个输出参数就没必要存在了。

Q13软件一次读 1600，DMA 容量 2048，所以基本不会放满？

方向对，但理由不成立。

先拆「放满」的两个意思：

  1. DMA 里有没有数据？—— 永远有，它按 16 kHz 不停灌
  2. 会不会溢出（绕回覆盖未读数据）？—— 这才是你问的，正常不会

但你的算术里有个隐含错误假设：「软件攒到 1600 才去读，一次清空」。实际不是这样——关键在 mic.cpp:122 的第四个参数：pdMS_TO_TICKS(20)，而 1600 是请求上限。

20 ms × 16 样本/ms = 320 个样本 攒满 1600 需要 100 ms，但超时只有 20 ms

所以 i2s_read 几乎每次都「等到超时，拿着三四百个样本返回」，根本等不到 1600。真实水位：

水位 480 ┤ ╱╲ ╱╲ ╱╲ │ ╱ ╲ ╱ ╲ ╱ ╲ ← 每轮排空一次 0 ┤────╱────╲──────╱────╲──────╱────╲── 2048 ┼───────────────────────────────────── ← 容量线，差得远

那 2048 的意义是什么？是「余量」，回答这个问题：CPU 卡住多久，音频才会丢？→ 128 ms。

正常不会溢出，但原因不是「1600 < 2048」，而是软件在持续小批量排空，水位只有几百个样本。

Q14i2s_read 的超时具体是什么情况？

Arduino-ESP32 用 CONFIG_FREERTOS_HZ = 1000，所以 pdMS_TO_TICKS(20) = 精确 20 ms。i2s_read 是带截止时间的阻塞调用：

i2s_read(要 3200 字节, 最多等 20ms) │ ├─ DMA 里已经攒够 3200 字节？ ──是──▶ 立刻返回，bytes_read = 3200 │ └─ 否 ─▶ 【挂起当前任务】，等数据进来 ├─ 攒够 3200 字节 ──────▶ 返回，bytes_read = 3200 └─ 20ms 到，仍没攒够 ──▶ 返回手上有的，bytes_read = 部分值
情况耗时bytes_read
数据早就在 DMA 里等着~03200（满额）
等到攒满< 20ms3200（满额）
20ms 到了还没攒满= 20ms部分 ← 常态
超时 ≠ 出错。在 I2S 语境里，「超时」不是故障，而是「有多少给多少」。因为 20ms 超时永远比「攒满 1600」来得早，所以几乎每次都走这条路。

例外：CPU 卡顿过、DMA 积压超过 1600 时，调用会立刻返回满额——1600 只在「CPU 落后了正在追赶」时才真正用满。

阻塞 ≠ 忙等。等待期间任务被挂起（sleep），CPU 让给别的任务：NimBLE 协议栈、BT controller、IDLE。所以这 20ms 不是浪费——BLE 通信照常进行，这也是为什么主循环里敢用阻塞式读取。

为什么选 20 ms：太长（100ms）会让主循环被卡住、按键/BLE/照片全变迟钝；太短（1ms）会频繁空手而归。20ms 至少能拿到 ~320 个样本「有活干」，又不至于卡太久。

软件接收层

数据第一次进入应用代码

Q15MIC_GAIN 增益倍数是什么？

config.h:131 —— #define MIC_GAIN 2。软件数字增益：拿到采样后把每个样本的数值放大几倍。当前值 2，即放大 2 倍（约 +6 dB）。

if (MIC_GAIN != 1) {
    for (size_t i = 0; i < samples_read; i++) {
        int32_t sample = (int32_t) i2s_read_buffer[i] * MIC_GAIN;   // 用 int32 防溢出
        if (sample > 32767)  sample = 32767;                        // 限幅
        if (sample < -32768) sample = -32768;
        i2s_read_buffer[i] = (int16_t) sample;
    }
}
  1. 发生在采样之后——纯软件运算，不改硬件。所以信号和底噪一起被放大
  2. 不是 AGC——写死的固定倍数，不根据音量动态调整
  3. 调太大会削波——放大到限幅就产生削波失真，听感发破

为什么设为 2：XIAO ESP32S3 Sense 内置 PDM 麦克风输出电平偏低，抬高一档让信号更接近满量程、编码更有效。属于实测调出来的经验值。

Q16onMicData(data, samples) 回调解释

回调函数——由 mic 模块在「数据准备好了」时反过来调用你的函数。核心思想：别来找我，我会找你。它由四块拼成：

① 类型定义（mic.h:8）

typedef void (*mic_data_handler)(int16_t *data, size_t samples);

② 注册（app.cpp:856）—— 传函数名，不是 onMicData()（那是调用）：

mic_set_callback(onMicData);

③ 保存（mic.cpp:109-112）与 ④ 调用（mic.cpp:140-142）：

static mic_data_handler audio_callback = nullptr;
void mic_set_callback(mic_data_handler callback) { audio_callback = callback; }
...
if (audio_callback != nullptr) {
    audio_callback(i2s_read_buffer, samples_read);   // ← 反向调用
}

nullptr 检查必须——没人注册时空指针会崩。回调本体只有一行：

PCM 环形缓冲

第一个软件缓冲：把不定长的输入变成整齐的帧

Q17写入环形缓冲的过程

int opus_receive_pcm(int16_t *data, size_t samples)
{
    if (pcm_ring_buffer == nullptr) return -1;

    for (size_t i = 0; i < samples; i++) {
        size_t next_write = (ring_write_pos + 1) % AUDIO_RING_BUFFER_SAMPLES;   // ①
        if (next_write == ring_read_pos) {                                      // ②
            ring_read_pos = (ring_read_pos + 1) % AUDIO_RING_BUFFER_SAMPLES;    // ③ 丢最旧
        }
        pcm_ring_buffer[ring_write_pos] = data[i];                              // ④
        ring_write_pos = next_write;                                            // ⑤
    }
    return 0;
}

写入一个样本的 5 步（用 N=8 示意）：

初始: ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐ │ │ │ a │ b │ c │ │ │ │ └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘ ↑ ↑ read=2 write=5 ① next_write = (5+1) % 8 = 6 ← 先算"写完之后指针到哪" ② 6 == read(2) ? 否 ← 不会撞上读指针 → 没满 ④ buf[5] = x ← 写进【当前】write 位置 ⑤ write = 6 ← 指针前移 结果: ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐ │ │ │ a │ b │ c │ x │ │ │ └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘ ↑ ↑ read=2 write=6

顺序很关键：先算指针 +1 判断满没满（①②），再往当前位置写（④）——不是先写再判断。

绕回（wrap-around）：写第 3 个样本时 next_write = (7+1) % 8 = 0，指针回到开头——这就是「环形」。此时可读数据在物理上被切成两段，所以读端必须也用 % N 逐字节取，不能 memcpy 一把拷。

满了：丢最旧的。假设 read=5, write=4（已满）：

① next_write = (4+1) % 8 = 5 ② 5 == read(5) ? 是！ ← 再写就会覆盖还没读的 a ③ read = 6 ← 【丢最旧的 a】 ④ buf[4] = i ⑤ write = 5

读端下次读到的是 b，a 永远丢了。这是「丢最旧、保最新」策略——对实时音频是对的：宁可丢一段旧声音，也不能让新声音因为没人取而卡住。反过来会导致延迟无限增长。

三个设计要点：

  1. 为什么「先算后写」：判断的是「推进之后会不会撞上读指针」，保证写端永远不会覆盖 read_pos 指向的未读数据（除非满，那时主动丢弃）。
  2. 为什么牺牲一个格子：判满是 next_write == ring_read_pos，所以最满时 write 比 read 落后一格，可用容量是 N−1 = 7999。因为「空」定义为 write == read，不留一格的话「满」也是 write == read，两种状态分不清。
  3. 为什么 volatile：告知编译器别优化掉重复读取。但本项目写和读都在同一个 loopTask 里，其实没有真正并发——这个 volatile 更像防御性写法。

实际可用是 7999 —— 因为判满机制牺牲一格（见 Q17）。分配在 PSRAM（opus_encoder.cpp:31，MALLOC_CAP_SPIRAM）。

别混淆：opus_input_buffer（320 样本）和 opus_output_buffer（160 字节）名字里也有 "opus"，但它们是编码器的输入/输出暂存，不是环形缓冲。

为什么 500 ms 比 DMA 的 128 ms 大得多？因为三层缓冲逐级放大——越往下游卡顿来源越不可控。

这 500ms 是「最大蓄水池」，不是「常态水位」——正常运行时读写速度相当，缓冲接近空，不增加延迟。但真涨满就意味着 500ms 延迟，所以容量大是安全边际，不是可挥霍的预算。

Q19pcm_ring_buffer[ring_write_pos] = data[i]; 每次写 2 字节吗？

是的，每次 2 字节 —— 但要注意：下标单位是「样本」，不是「字节」，×2 是编译器自动做的。两边都是 int16_t。

pcm_ring_buffer (int16_t *) 下标: 0 1 2 3 ... 7999 ┌────────┬────────┬────────┬────────┬─────┬────────┐ │ 2 字节 │ 2 字节 │ 2 字节 │ 2 字节 │ ... │ 2 字节 │ └────────┴────────┴────────┴────────┴─────┴────────┘ 字节地址: 0 2 4 6 15998

编译器实际生成的是 *(pcm_ring_buffer + ring_write_pos * 2)。所以 pcm_ring_buffer[3] 落在字节地址 6，(ring_write_pos + 1) 里的 +1 是 +2 字节。一次调用总量 = samples × 2 字节。

为什么不用 memcpy：环形缓冲可能绕回，memcpy 会越界。逐样本拷贝慢一点但永远安全。

对比记忆：int16_t * 的 p[3] = 字节 6；uint8_t * 的 p[3] = 字节 3。指针算术单位永远是元素大小。

不是同一块内存。pcm_data 是 opus_input_buffer 的形参别名，而 opus_input_buffer 的内容是从 pcm_ring_buffer 拷贝来的。

Opus 编码

640 字节 PCM 变成 80 字节

Q21opus_process() 一次读多少？没攒够 320 会卡吗？

一次固定读 320 个样本（= 20 ms），而且会循环读，直到缓冲里剩不足 320 为止。它读的是 PCM 环，不是「opus 输出环」——pcm_ring_buffer 是麦克风灌进来的原始 PCM。整个函数的方向是「入」不是「出」。

void opus_process()
{
    ...
    while (ring_buffer_available() >= OPUS_FRAME_SAMPLES) {      // ← 320
        for (size_t i = 0; i < OPUS_FRAME_SAMPLES; i++) {
            opus_input_buffer[i] = pcm_ring_buffer[ring_read_pos];
            ring_read_pos = (ring_read_pos + 1) % AUDIO_RING_BUFFER_SAMPLES;
        }
        int encoded_bytes = opus_encode_frame(opus_input_buffer, OPUS_FRAME_SAMPLES);
        if (encoded_bytes > 0 && encoded_callback != nullptr) {
            encoded_callback(opus_output_buffer, encoded_bytes);
        }
    }
}

320 是 Opus 的硬性帧长——它只接受 2.5 / 5 / 10 / 20 / 40 / 60 ms：

帧长 @16kHz样本数
5 ms80
10 ms160
20 ms320 ← 本项目
40 ms640
这轮积压编码帧数剩余
8000（满）25 帧0
5001 帧180
3190 帧319

用 >= 不是 ==：剩不足 320 的零头留在缓冲里，和下次新数据拼成完整帧。

没攒够 320 不卡，立刻返回。条件不成立 ≠ 阻塞等待，而是跳过循环体，直接 return，一毫秒都不等。对比 i2s_read：那个阻塞最多 20ms（等待有价值，让出 CPU 给 BLE 任务），而这里等也没用——数据自己会来，阻塞只会拖慢主循环。

是逐样本拷贝不是 memcpy——因为环形数据可能被切成两段。memcpy 会越界。

Q22opus_process() 读出的速率是 20 ms 一次吗？

不是。「20ms」是一帧音频的时长，不是函数的调用间隔。

值由谁决定性质
一帧消耗的音频时长320 ÷ 16000 = 20 msOpus 帧长规定精确固定
函数被调用的间隔≈ 25~30 ms主循环节奏浮动

opus_process() 里没有任何定时器、没有 delay(20) —— 它是被主循环「顺便」调用的。一轮主循环 ≈ i2s_read 阻塞 20ms + delay(5) + 其他几 ms ≈ 25~30 ms。

长期平均被「钉死」在 50 帧/秒（16000 ÷ 320），除以 35 次/秒 ≈ 1.4 帧/次——「大多数时候 1 帧，偶尔 2 帧」，通过不均匀凑出均匀。

时间轴（一轮 = 25~30ms） │←──── 轮 1 ────→│←──── 轮 2 ────→│←──── 轮 3 ────→│ 麦克风灌入： 448 个 448 个 448 个 opus_process: 读1帧(320) 读1帧(320) 读2帧(640) ← 能读多少读多少

它是「数据驱动」不是「时钟驱动」。为什么不用 20ms 定时器？因为主循环其他活儿会让定时器失约，错过就要补偿；而「每次主循环都调，能读多少读多少」完全自适应，代码极简，只要主循环周期 < 500ms（环容量）就永不丢数据。

Q23为什么「320 样本 → 160 字节」这个理解不对？

因为 320 和 160 之间根本不存在换算关系——它们管的是完全不同的两件事：

常量值单位管什么
OPUS_FRAME_SAMPLES320样本输入：一次喂多少
OPUS_BITRATE32000bps决定输出多大 ← 关键
OPUS_OUTPUT_MAX_BYTES160字节容量上限，不是实际产出

实际输出用码率算，不是用 320 算：

每帧字节 = 32000 bps ÷ 8 ÷ 50 帧/s = 80 字节 输入 编码 输出 ┌───────────────┐ ┌──────────┐ ┌──────────────┐ │ 320 个样本 │ │ Opus │ │ ~80 字节 │ │ = 640 字节 PCM│ ─────▶ │ 压缩 8:1 │ ─────▶ │ (浮动 60~140) │ └───────────────┘ └──────────┘ └──────────────┘ ↓ 放进 ┌──────────────────────┐ │ opus_output_buffer │ │ 容量 160，只用了 80 │ │ ▓▓▓▓▓▓▓▓░░░░░░░░░░░ │ └──────────────────────┘

160 是「箱子有多大」，不是「装了多满」。为什么定 160？因为 Opus 是 VBR（每帧大小浮动），80 是平均值，160 = 平均的 2 倍，给峰值留余量。超过 160 时 Opus 不报错、不截断，而是主动降这一帧的音质把数据塞进去。

「必须 320 吗」—— 不是必须，是选择：

选哪个延迟压缩效率BLE 开销
160（10ms）低较差高（100 包/秒）
320（20ms）中好中（50 包/秒）
640（40ms）高最好低（25 包/秒）

20ms 是语音的经典折中点。

Q24每帧输出 80 字节，由声音复杂度决定吗？

是，但只是一半的原因。是「声音复杂度」和「目标码率」两股力量拉扯的结果：复杂度决定这一帧想用多少，码率决定长期平均只能用多少。

VBR = 1 就是「允许浮动」的开关（opus_encoder.cpp:74-75）：

设置含义
OPUS_VBR = 1可变码率，每帧大小可不同
OPUS_VBR_CONSTRAINT = 0不约束浮动幅度

如果改成 OPUS_SET_VBR(0)（CBR），每帧就会固定约 80 字节。

这 20ms 是什么声音大概多少字节
静音 / 只有底噪10 ~ 40
平稳元音（"啊——"）50 ~ 70
正常说话70 ~ 90
语速快 + 噪音 + 爆破音100 ~ 140
音乐 / 混杂噪声140 ~ 160（逼近上限）

规律：周期性、平稳的声音（元音）→ 预测得准 → 少字节；突变、无规律的声音 → 难预测 → 多字节。这正是 SILK 的 LPC 预测在做的事。

速率控制的机制是滚动账本：最近几帧用多了就收紧，用少了就放宽，长期平均被拉回 32 kbps。源码在本地：celt/rate.c（比特分配）、silk/control_SNR.c（SNR 调节）。

注意帧长和复杂度是两个独立维度：同样 20ms，静音可能 15 字节，摇滚乐可能 155 字节——差 10 倍。

Q26单帧输出写到 encoded_bytes 还是 opus_output_buffer？

两个都去，但去的东西不一样：压缩后的数据（~80 字节）进 opus_output_buffer；encoded_bytes 只拿到一个数字——实际写了多少字节。

决定性论据：类型装不下。opus_int32 encoded_bytes 是 32 位整数 = 4 字节，物理上装不下 80 字节的数据。它只能是个「长度」。

opus_output_buffer （容量 160 字节） ┌──────────────────────────────────────┬───────────────────────────┐ │ 有效数据：78 字节 │ 未使用（上次的残留） │ │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │ ░░░░░░░░░░░░░░░░░░░░░░░ │ └──────────────────────────────────────┴───────────────────────────┘ ↑ ↑ 数据本身 encoded_bytes = 78（有效到这儿）

160 和 78 的区别：缓冲有 160 容量，这次只填了 78。encoded_bytes 标出有效部分的终点——不然不知道 160 里哪些是真数据。

encoded_callback(opus_output_buffer, encoded_bytes);

这是 C 的经典模式：「缓冲区 + 长度」。只给指针 → 不知道有效数据到哪结束；只给长度 → 不知道数据在哪；两个都给 → 完整描述「从地址 X 开始的 N 个字节」。输入侧也是：pcm（指针）+ frame_size（长度）；输出侧对称：data（指针）+ 返回值（长度）。

它是「编码器」和「BLE 发送」之间的中转站——把刚编码好的一帧暂存进发送队列，至于什么时候发，它不管。

它做的三件事（app.cpp:330-359）：① 校验长度（if (len > OPUS_OUTPUT_MAX_BYTES) return;）；② 加 2 字节长度前缀，写进发送环；③ 溢出保护——检查「写下去会不会撞上读指针」，会的话放弃这一帧。

它不发数据！真正的发送在 processAudioTx()（app.cpp:380-417）。opus_process() 触发这个回调只是暂存，主循环里另一处才真正发 BLE。

为什么拆两步？因为编码和发送的节奏对不上：编码由 Opus 帧长定时定量，不能停（麦克风一直在进数据）；发送要看 BLE 连接状态和拥塞。发送环就是这两者之间的缓冲池。

为什么要加 2 字节长度前缀？因为 Opus 是 VBR——每帧大小不一样（60~160 字节浮动）。而 audio_tx_buffer 是字节流，不知道帧的边界：

不加前缀：[帧1 80字节][帧2 95字节][帧3 62字节] ← 读端不知第一帧到哪结束 加前缀： [80][帧1][95][帧2][62][帧3] ← 一看 95 就知道接下来 95 字节是一帧

「长度前缀 + 变长数据」是字节流里划分消息边界的标准做法。

Q29audio_tx_buffer 为什么是 16 × 162？16 是环的大小吗？

对，16 就是环形缓冲能装的「帧数」 —— 但要补充：它是「最坏情况保证」，不是「实际只能装 16 帧」。

部分值含义
AUDIO_TX_RING_BUFFER_SIZE16帧数
OPUS_OUTPUT_MAX_BYTES + 2160 + 2 = 162每帧占多少字节
乘积2592缓冲总字节数

为什么 +2 不是 +160？因为 onOpusEncoded 写进环时每帧前加了 2 字节长度前缀：

┌────────┬────────┬──────────────────────────┐ │ 长度低 │ 长度高 │ Opus 数据（最多 160） │ └────────┴────────┴──────────────────────────┘ └── 2 字节 ──┘└────── 最多 160 字节 ──────┘
16 是「最坏情况保证」，实际能装约 31 帧。容量是按「每帧都取最大值 160 字节」算的（16 × 162 = 2592），意思是哪怕每帧都顶到 160 上限也保证能装 16 帧。但实际帧平均只有 ~80 字节，所以 2592 ÷ 82 ≈ 31 帧。好处：不管 Opus 吐出多复杂的帧，环都不会溢出。

它是「字节环」不是「帧环」——虽然容量「按帧数」命名，但指针和取模都在字节上做（% AUDIO_TX_BUFFER_SIZE = 2592）。对比 PCM 环是按样本取模（8000），因为那个环的数据是定长的。

16 帧对应 16 × 20ms = 320 ms（典型 80 字节帧则约 620ms）——这就是它能吸收的最长 BLE 拥塞时间。

和 PCM 环不同的是溢出策略：PCM 环满了丢最旧的（保实时性），发送环满了丢最新的（return 放弃这一帧，保持队列顺序）。

Q30解释 memcpy(...) 和 setValue(...) 这两行

void broadcastAudioPacket(uint8_t *data, size_t len)
{
    if (!connected || !audioSubscribed || audioDataCharacteristic == nullptr) return;

    // Build packet: 2 bytes index + 1 byte sub-index + data
    audio_packet_buffer[0] = audioPacketIndex & 0xFF;            // 序号 低字节
    audio_packet_buffer[1] = (audioPacketIndex >> 8) & 0xFF;     // 序号 高字节
    audio_packet_buffer[2] = 0;                                  // 子序号

    memcpy(audio_packet_buffer + AUDIO_PACKET_HEADER_SIZE, data, len);        // ①
    audioDataCharacteristic->setValue(audio_packet_buffer, len + AUDIO_PACKET_HEADER_SIZE);  // ②
    audioDataCharacteristic->notify();                            // ③ 真正发出

    audioPacketIndex++;
}

① memcpy —— 把 Opus 数据搬进缓冲，但故意从偏移 3 开始（前 3 字节是包头）。目的地是 audio_packet_buffer + 3，源是 data，拷 len 字节。

注意这里的 +3 和 pcm_ring_buffer[3] 完全不同：int16_t *pcm_ring_buffer 的 p[3] → 字节 6（×2）；uint8_t *audio_packet_buffer 的 +3 → 字节 3（×1）。指针算术单位永远是元素大小。

② setValue —— 语义是「把 buf 开头的 size 个字节设为特征值的当前内容」。为什么是 len + 3 不是 len？因为要送的是整个包（包头 + 负载）。只写 len 会把 3 字节包头切掉，接收端无法判断丢包。setValue 只是装填，真正发出的是下一行的 notify()。

那 3 个字节的头是：[0][1] = audioPacketIndex（小端序，16 位包序号）、[2] = 子序号（为分片预留，当前恒为 0）。

为什么需要包序号？因为 BLE 通知可能丢包、可能乱序——手机收到 100, 101, 103 就知道 102 丢了，可以请求重传或做丢包隐藏；序号也能用来重排序。Opus 本身支持丢包隐藏（PLC），但前提是知道丢了包。这个格式就是 Omi 协议规定的。

audio_packet_buffer （容量 163 字节 = 160 + 3） ┌──────────┬──────────┬──────────┬────────────────────────────────┬─────────┐ │ [0] │ [1] │ [2] │ [3] ... [3+len-1] │ 未使用 │ │ 序号低 │ 序号高 │ 子序号 │ Opus 帧数据 (len 字节) │ │ └──────────┴──────────┴──────────┴────────────────────────────────┴─────────┘ └──── 3 字节包头 ────┘└──────────── 负载 ────────────┘ └──────────────── len + 3 字节 ─────────────────────┘ 典型值：len ≈ 80 → 包总长 ≈ 83 字节

边界安全靠上游的校验保证（app.cpp:396 的 len > OPUS_OUTPUT_MAX_BYTES），所以 len + 3 ≤ 163 = 缓冲容量。

配套条件：BLE MTU。包总长最大 163 字节，超过 BLE 默认 ATT MTU（23 字节，负载 20）。所以前提是手机连接时协商了足够大的 MTU（≥ 166）。如果 MTU 太小，notify() 会截断或失败——这是调试「音频发不出去」时该查的一个点。
